# 先沟通、按需试验的功能开发流程

> 2026-08-29 · 方案已获用户确认；核心修改、本地回归与 Codex 权威行为验收完成。本文仅记录本次变更，运行规则仍以 canonical actions 为准。

## 做什么

让 project-workflow 帮助用户和 AI 先理解问题、验证关键假设，再根据确认的行为实现与验收。取消 LIGHT／FULL 和强制三件套，减少文件维护、重复提问和上下文加载。用户已明确确认：不能因更新文档打断交流、丢失上下文或削弱测试。

范围是本仓库的核心方法论、canonical actions/reviewers、模板、建文件脚本、现有测试以及 Claude/Codex 双端适配。保留 9 个动作、现有项目目录、当前事实与归档的职责。此次不修改 project-blueprint、PMO 项目、已安装插件缓存或其他使用方项目，不自动提交、发版或推送。

## 确认的做法

- 正常顺序是沟通 → 必要时调查/试验 → 确认方案与验收 → 实现并验证；它不是每一步都要审批的固定流水线。用户已经确认过的方向和实施授权继续有效，尚未写入 spec 也成立；改变已确认边界须有新的用户决定，明确的“把 A 改成 B”本身即可构成确认，不再复问。普通细节不重问。权限不足、方向改变或项目明确要求的阶段交接仍须停下确认。
- 有关键不确定性才试验；试验前说清问题与判断方法。只做已获授权的有限试验，不把它扩大为正式实现，不外传未获许可的数据。不能试验时如实记录限制，不把未验证假设写成事实。
- 需要持久记录时默认仅创建 `docs/specs/changes/<NNN>-<slug>/spec.md`。小修复可以不新增记录，已有活动记录直接复用。不要提前创建 plan、tasks、evidence 目录或另一套分流标签。
- 一份 spec 说明问题与边界、方案及必要依据、验收例子与预期、最终验证结果。章节是写作提示；不检查字数，不填空章节，不以是否有完整标题判断就绪。已由当前事实说明的行为用引用和本次差异表达，不重写整个产品域。
- 实施中继续发现任务和边界。普通细节直接推进；涉及方向、范围、数据、授权、重要成本或验收的新发现，先暂停受影响的工作并解释，确认后局部修订再继续。此项来自用户补充：“开发过程中，如果有类似情况也可以停下主动和用户沟通，再确认更新文档，然后继续实施”。不重开整个功能，不重审未受影响的决定。
- 先回应正在讨论的问题，在结论形成、准备实施或交接时集中写回。长对话可能丢失重要信息时提前保存简短摘要。只保存已确认决定及原因、仍未解的问题、影响决策的证据；不复制整段聊天或日志，不把试验猜测升级为用户决定。
- 测试放在项目已有测试位置，文档引用测试和必要的可复现证据。较长设计或清单真正影响阅读、交接时才拆文件，接受规则仍只有一处。无需额外报告来复述同一结果。
- 试验观察、确认的预期和实现验证结果分别表达。实际输出不自动成为正确答案；失败应修复实现，或在需求确实改变且获确认后修订预期，并使受影响的旧证据失效。不能改文档来掩盖失败。
- 检查和独立审查按行为与实际风险决定，保留代码运行、项目约定、需求符合性三个视角。少量代码或一份 spec 不豁免权限、数据迁移等必要验证；增加文件也不自动增加审查层。
- 文档只按当前任务需要读取。接续时读取相关记录、剩余工作与必要证据，不重读整套方法论和归档，不人为重置会话。新测试引用缺失或摘要丢掉否定条件时不能报告就绪。
- 活动记录统一由 `spec.md` 持有接受状态和交付结果；plan、tasks 等仅在确有帮助时作为附件。升级前的旧记录已归档并保持历史原貌，不进入活动执行，也不建立兼容或迁移流程。

### 依据与实施约束

用户在本次会话中依次确认了单文件、按需拆分、自然沟通及测试不被削弱。仓库的 [feature-init](../actions/feature-init.md)、[feature-done](../actions/feature-done.md) 和 [建文件脚本](../../scripts/materialize-feature-artifact.cjs) 表明，旧车道影响文件生成、实施入口、评审和收据；不能只改文案。

外部资料用于解释取舍，不是额外运行规则：[BDD](https://cucumber.io/docs/bdd/) 以具体例子形成共识；[假设驱动开发](https://www.thoughtworks.com/en-us/insights/articles/data-driven-hypothesis-development) 先定判断条件再试验；[Shape Up](https://basecamp.com/shapeup/4.1-appendix-02) 允许小团队省去正式结构；[OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/explore.md) 有不产出文档的探索入口，但不照搬其多文件布局。

保留原有防覆盖、正确目标根、符号链接边界、编号冲突、失败回滚、权限约束、归档链接和真实性检查。只替换旧文件套餐/格式对应的断言；不得删掉仍有效的安全回归来换取通过。

## 怎样验收

具体对话输入和失败判据只维护在 [现有场景集](../../tests/fixtures/feature-init-scenarios/expected.json) 的 `conversation-*` 条目中，执行方式见 [场景协议](../examples/feature-init-scenario-matrix.md#conversation-first-change-acceptance)。覆盖：

- 先回答问题，不提前生成文件或实现；允许的有限试验可继续推进理解。
- 试验不满足预设条件时如实保留反例，不能直接写成验收成功。
- 多轮讨论不逐句落盘、重复确认；最终结论保留明确否定和被取代的决定。
- 接续时保留未解决问题和授权边界，不把压缩摘要当成扩大权限的依据。
- 普通需追踪功能仅用一份 spec；少量授权逻辑变更仍有风险验证。
- 验证失败不能通过修改 spec 或删除断言变成通过。
- 外部试验权限不足时不调用、不伪造结果，继续可用的本地分析。

这些是待运行的行为验收，不是“已通过”的模型测试。对话测试需保存实际宿主、输入、输出、工具动作和可复核结果；模型未运行必须明确标记。静态校验仅证明测试材料自洽。
