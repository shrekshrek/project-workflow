# 功能记录与验证实践指南

本指南说明怎样写、使用和维护功能记录；触发、授权和检查规则只由 [canonical actions](actions/README.md) 定义。

## 1. 先理解问题

从用户遇到的问题和具体例子开始，查看必要的代码、数据与测试。关键假设不清楚时做获准的有限试验，先确定怎样判断结果，再执行；不要求每个功能都做原型。得到足够依据并确认范围、方案和验收后，再开始正式实现。

默认不假设用户了解仓库结构、实现方式或测试术语。先用业务结果解释“这一步想证明什么、通过或失败意味着什么”，再按需说明单元、集成、E2E 等技术名称；这不降低用户对产品方向、风险、时间和费用的决策权。实现前对齐结果、边界、方向、理由和验证安排；切片内普通步骤不反复索要“继续”，实质问题立即暂停，有意义的切片结束时用实际结果和证据帮助用户判断后再继续。

这不是严格的单向流程。实现会带来新认识；普通细节可以继续，影响方向的新发现回到沟通。文档承担保存共识和验证依据的作用，不能代替理解问题。准确的继续/暂停边界见 [feature-init](actions/feature-init.md)。

## 2. 默认一份够用的记录

需要持久追踪的功能默认只创建：

```text
docs/specs/changes/<NNN>-<slug>/spec.md
```

简单小改可以不新增记录；已有活动记录覆盖当前工作时直接复用。不选择文档套餐，不预建 plan、tasks 或 evidence 目录。保留原有目录和编号便于引用、归档。

内容只需让下一个读者知道：做什么、为什么这样做、怎样算对、实际验证如何。章节可以合并或改名；没有内容就省略，不凑标题、字数、表格或测试数量。短实施清单也可以直接写在 spec 中，不强迫拆到另一份文件。

已有当前事实用引用和本次差异说明，不重新抄一遍整个产品域。已有独立设计/任务文件在有用时继续使用；后续内容确实长到影响阅读和交接时才拆出，并引用唯一的接受规则。测试代码进入项目原有测试目录，spec 引用它。长试验脚本/结果仅在复现需要时另存，敏感数据不得写入公共记录。

可读的单文件例子见 [feature record](examples/feature-record.md)。它是合成例子，不是每个项目都要复制的格式。

## 3. 记录结论，不打断对话

先回答用户当前的问题。在结论形成、准备实施或交接时集中更新；长对话中重要信息可能丢失时，提前保存一小段可靠摘要。不逐轮落盘，不把每次写文件变成审批。

保留确认的决定及必要理由、明确否定、被取代的规则、未决问题和授权范围。外部解释、冲突取舍等重要决定附来源，普通需求不再复制一份来源表。不要复制整段聊天和日志，也不要压缩掉“不允许”“尚未决定”等关键信息。

新会话读取相关记录和剩余工作，再按需读来源；不重新加载全部规范/归档，不因为文档更新清空上下文，不重复确认已经决定的事。项目工作约定仍由 `AGENTS.md` 拥有，功能记录不重复它。

## 4. 用具体例子验收

确认的例子说明输入/场景与预期结果；实施后用实际测试或可复核观察验证。三者不要混淆：

- 试验观察：某次输入实际得到了什么，在哪种条件下。
- 接受规则：用户确认系统应该怎样表现。
- 交付证据：项目实现是否满足该规则。

验证强度随阶段改变：开发前只解决会改变方案的关键未知；开发中用聚焦检查反馈当前改动；开发后才根据接受义务和风险选择完整证据。不要用开发前试验冒充交付，也不要用完整交付门槛阻塞已有充分依据的实现起点。

失败的试验可以帮助排除方案；未运行就写未运行。测试失败不能通过降低预期或删除断言变成成功。真正改变需求时先确认，修订相关规则和测试，并让受影响的旧证据失效；其他验证继续保留。

复用最小充分证据，一个测试可以覆盖多个相关要求；额外层级/矩阵要解决不同风险或明确项目要求。权限、迁移、恢复等风险不能因为代码少或文档短而省略验证。

验证从最便宜的有效证据开始，按剩余风险渐进扩大。必要的低成本检查失败后，先修复并复验受影响证据，不继续无关的高成本批次；准备声明 READY 时仍需完成全部适用交付义务。

耗时长、付费、外部或不透明的检查启动前说明用户判断是否开始所需的范围、成本、可见进度、中断后果和较小替代方案。无法观察精确进度时如实说明，不编造百分比。

实施前的 [spec-quality-check](actions/spec-quality-check.md) 检查依据是否足以行动；交付的 [feature-done](actions/feature-done.md) 检查实现是否兑现。两者不能互相代替。实际对话行为也不能由静态文件校验代替。

## 5. Spec 生命周期

草稿用于讨论；已确认的行为指导实施；已实现说明当时交付验证通过。状态不等于用户授权，也不意味着记录永远代表现状。

活动且未归档的记录出现重要新发现时，先解释影响和建议、取得必要决定，然后通过 [spec-revise](actions/spec-revise.md) 局部更新并继续。普通任务细化不需要新 feature、重新访谈或全套重审。只修实现错误时保持原验收，复验受影响部分。已归档的后续变化使用 successor feature，历史正文不改写。

最终结果由 feature-done 追加到活动记录 `spec.md` 的 `## Proof Bundle`。收据有真实下游消费者，创建功能时不预填空字段。详细日志留在测试输出或适当证据位置，正文只留结果与引用。

[feature-archive](actions/feature-archive.md) 负责在 READY 后将仍有效的持久行为合并到 `docs/specs/<area>.md`，再移动整个变更目录到 `docs/specs/changes/archive/`。当前事实按现状替换维护；归档保存历史，日常检索排除它。外部 tracking 不是启动所选 child 的前置条件，也不要求额外仓库索引或台账。

架构/模块边界、持久跨功能决定或取代既有 ADR 才需要 ADR。不要把每次小修订都变成一份决策文档。仅在存在实际矛盾时用 [spec-reconcile](actions/spec-reconcile.md)，不按文档年龄批量整理。

## 6. 常见误用

- 写完模板就认为问题已澄清：应检查真实例子、依据和关键未决事项。
- 每轮对话同步多份文件：在自然节点集中保存结论，让用户继续谈问题。
- 只保存“采用方案 B”：重要取舍保留理由，避免接续时重新猜测。
- 把全部实现任务提前固定：实施发现新任务正常，关键是接受规则不被偷偷改变。
- 把原型通过当成交付：仍需验证集成后的实际项目。
- 同一条验收写在 spec、plan、tasks 三处：保留一个内容所有者，其他位置引用。

## 参考

- [Cucumber BDD](https://cucumber.io/docs/bdd/)：讨论具体例子，再形成可验证的共同理解。
- [Thoughtworks 假设驱动开发](https://www.thoughtworks.com/en-us/insights/articles/data-driven-hypothesis-development)：先定判断条件，再用有限试验学习。

- [OpenSpec Explore](https://github.com/Fission-AI/OpenSpec/blob/main/docs/explore.md)：探索入口与正式产物分开；本项目不照搬其文件布局。
