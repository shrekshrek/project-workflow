# 功能记录与验证实践指南

本指南说明怎样写、使用和维护功能记录；何时使用、需要什么授权、怎样检查，以 [actions](actions/README.md) 为准。

## 1. 先理解问题

从用户遇到的问题和具体例子开始，查看必要的代码、数据与测试。关键假设不清楚时做获准的有限试验，先确定怎样判断结果，再执行；不要求每个功能都做原型。得到足够依据并确认范围、方案和验收后，再开始正式实现。

不要假设用户熟悉仓库和测试术语。先讲清这一步要验证什么、通过或失败意味着什么，再按需解释技术名称。产品方向、风险、时间和费用仍由用户决定。实现前在对话里讲清功能如何运行、哪些选择需要用户判断。实施与交接遵循 [feature-init](actions/feature-init.md#implementation-scope-stop)。

这不是严格的单向流程。实现会带来新认识；普通细节可以继续，影响方向的新发现回到沟通。文档用来保存决定和验证依据，不能代替理解问题。何时继续或暂停，见 [feature-init](actions/feature-init.md)。

## 2. 默认一份够用的记录

需要持久追踪的功能默认只创建：

```text
docs/specs/changes/<NNN>-<slug>/spec.md
```

简单小改可以不新增记录；已有活动记录覆盖当前工作时直接复用。不选择文档套餐，不预建 plan、tasks 或 evidence 目录。保留原有目录和编号便于引用、归档。

内容只需让下一个读者知道：做什么、为什么这样做、怎样算对、实际验证如何。默认章节沿用模板，无内容则省略，业务细分放在下一级；结构例外遵循 [feature-init 的记录规则](actions/feature-init.md#record-and-authorization)，不凑字数、表格或测试数量。短实施清单也可以直接写在 spec 中，不强迫拆到另一份文件。

已有产品文档就引用，只说明本次差异。独立设计或任务文件仍有用就继续用；确实有助于阅读、交接或独立使用时再拆文件，验收规则只保留一份，其他位置引用。测试代码进入项目原有测试目录，spec 引用它。长试验脚本/结果仅在复现需要时另存，敏感数据不得写入公共记录。

可读的单文件例子见 [feature record](examples/feature-record.md)。它是合成例子，不是每个项目都要复制的格式。

## 3. 记录结论，不打断对话

先回答用户当前的问题。在结论形成、准备实施或交接时集中更新；长对话中重要信息可能丢失时，提前保存一小段可靠摘要。不每轮都写文件，不把每次写文件变成审批。

保留确认的决定及必要理由、明确否定、替换了哪些旧规则、未决问题和授权范围。外部解释、冲突取舍等重要决定附来源，普通需求不再复制一份来源表。不要复制整段聊天和日志，也不要压缩掉“不允许”“尚未决定”等关键信息。

新会话读取相关记录和剩余工作，再按需读来源；沿用已确认的范围和授权。用户主动修订时，可以简短核对新决定和影响。项目约定统一放在 `AGENTS.md`，功能记录不重复。

## 4. 用具体例子验收

确认的例子说明输入/场景与预期结果；实施后用实际测试或可复核观察验证。三者不要混淆：

- 试验观察：某次输入实际得到了什么，在哪种条件下。
- 接受规则：用户确认系统应该怎样表现。
- 交付证据：项目实现是否满足该规则。

验证强度随阶段改变：开发前只解决会改变方案的关键未知；开发中用聚焦检查验证当前改动；开发后按验收要求和风险完成验证。前期试验不等于交付通过，也不必在开工前完成交付阶段的全部检查。

失败的试验可以帮助排除方案；未运行就写未运行。测试失败不能通过降低预期或删除断言变成成功。真正改变需求时先确认，修订相关规则和测试，并让受影响的旧证据失效；其他验证继续保留。

用足以说明问题的最少检查，一个测试可以覆盖多个相关要求；增加测试层级或场景组合，应是为了检查不同风险或满足项目要求。权限、迁移、恢复等风险不能因为代码少或文档短而省略验证。

先做成本低、能发现问题的检查，再按剩余风险扩大范围。必要检查失败后，先修复并复验，暂停无关的高成本检查；声明 READY 前仍要完成全部适用的验收要求。

耗时长、付费、访问外部服务或过程难以观察的检查，启动前讲清范围、成本、如何看进度、中断后果，以及能否先做小范围验证。无法观察精确进度时如实说明，不编造百分比。

实施前的 [spec-quality-check](actions/spec-quality-check.md) 检查依据是否足以行动；交付的 [feature-done](actions/feature-done.md) 检查实现是否兑现。两者不能互相代替。实际对话行为也不能由静态文件校验代替。

## 5. Spec 生命周期

草稿用于讨论；已确认的行为指导实施；已实现说明当时交付验证通过。状态不等于用户授权，也不意味着记录永远代表现状。

活动且未归档的记录出现重要新发现时，先解释影响和建议、取得必要决定，然后通过 [spec-revise](actions/spec-revise.md) 局部更新并继续。普通任务细化不需要新 feature、重新访谈或全套重审。只修实现错误时保持原验收，复验受影响部分。已归档功能的后续变化新建功能记录（successor feature），不改写历史正文。

最终结果由 feature-done 追加到活动记录 `spec.md` 的 `## Proof Bundle`。这份交付记录供后续归档使用，创建功能时不预填空字段。详细日志留在测试输出或适当证据位置，正文只留结果与引用。

[feature-archive](actions/feature-archive.md) 负责在 READY 后将仍然有效的产品行为更新到 `docs/specs/<area>.md`，再移动整个变更目录到 `docs/specs/changes/archive/`。产品文档反映现状，归档保存历史，日常查找排除归档。拆出的功能不必先建外部任务，也不需要额外索引或台账。

改变架构或模块边界、形成多个功能长期共用的技术决定，或替换已有 ADR 时，才需要 ADR。不要把每次小修订都变成一份决策文档。仅在存在实际矛盾时用 [spec-reconcile](actions/spec-reconcile.md)，不按文档年龄批量整理。

## 6. 常见误用

- 写完模板就认为问题已澄清：应检查真实例子、依据和关键未决事项。
- 每轮对话同步多份文件：在自然节点集中保存结论，让用户继续谈问题。
- 只保存“采用方案 B”：重要取舍保留理由，避免接续时重新猜测。
- 把全部实现任务提前固定：实施发现新任务正常，关键是已确认的要求不被偷偷改变。
- 把原型通过当成交付：仍需验证集成后的实际项目。
- 同一条验收写在 spec、plan、tasks 三处：只在一处维护，其他位置引用。

- [Cucumber BDD](https://cucumber.io/docs/bdd/)：讨论具体例子，再形成可验证的共同理解。
- [Thoughtworks 假设驱动开发](https://www.thoughtworks.com/en-us/insights/articles/data-driven-hypothesis-development)：先定判断条件，再用有限试验学习。
